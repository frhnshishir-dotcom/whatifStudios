# M2: before and after (2026-11-27)

Both runs used the same script (`bench/server.mjs`, seeded bots) in the same cloud container (Node 22), one after the
other:
- **Before:** commit 55a377e (M1, no M2), in a scratch worktree, with the current script copied in.
- **After:** the M2 code.

These are **not laptop numbers**. On the laptop, run `npm run bench:server` and `npm run test:accept`
([README](README.md)).

Scenarios:
- `together-16`: 16 bots around Lumenfall.
- `spread-18`: three bots in each of the six villages.
- `travel-18`: as spread-18, and every 5 s one bot per village travels 400 m into new ground.

**Before M2, travel-18 broke down.** Regions were generated on the update loop, once a second, for every player. The
cache (64 regions) dropped regions players were standing in and generated them again. Over the run:
- 278 regions were generated on the loop, taking 34.3 s;
- one update took 13.9 s;
- only 70 updates ran in 40 s;
- the ground at most travel destinations was still not exact 14 s after arrival, and some never arrived within 20 s.

**After M2:**
- no region is generated on the loop;
- a traveller's ground is exact after 24 ms (median), and 1.2 s at worst.

## Memory

| Scenario | | Heap max | RSS max | Regions cached |
|---|---|---|---|---|
| together-16 | before / after | 49.2 / 42.2 MB | 305.5 / 464.8 MB | 9 / 9 |
| spread-18 | before / after | 46.7 / 50.5 MB | 379.6 / 550.4 MB | 63 / 63 |
| travel-18 | before / after | 42.7 / 46.0 MB | 393.4 / 665.5 MB | 64 / 138 |

**RSS is higher after M2.**
- **Workers:** each region worker is a separate V8 instance with its own blueprint and terrain, measured at 70–90 MB.
  Up to two run while regions are wanted, and they stop after 30 s idle. In a bench run they are busy throughout.
- **Cache:** it now grows with demand instead of discarding regions in use. travel-18 holds 138 regions (about 1.2 MB
  each), within its demand-sized capacity.

Heap use on the main thread is unchanged.
